# indus-two-regimes-code

The analysis code behind **"Two Sign-Regimes in the Indus Corpus: Templated Tablets and Marker-Anchored Seals"**
(Praveen Khanna, CHR 2027). Every number printed in the paper is generated by this code from one input file,
through the number pipeline in `numbers/`. Release `v1.0-chr2027`. MIT licence. Python 3.11, standard library only;
the one exception is the check of the compiled paper (`numbers/check_rendered.py`), which also calls the external
`pdftotext` tool (Poppler; Git for Windows ships it).

## What is here, and what is not

- `analysis/`: the measurement code (`spec_lib*.py`), the two runs (`run_core.py`, `run_full.py`), the readings of
  the specification where its text needed one (`SPEC_READINGS.md`), and `tests/`: synthetic tests only.
- `spec/`: the frozen measurement specification and the registrations it names, as they were frozen
  (`FREEZE_RECORD.md` gives the private repository's tag, commit and blob ids); see "Differences" below.
- `run_record/RUN_RECORD.md`: the record of the confirmation runs with the SHA-256 of every output.
- `numbers/`: the registry of every printed number (macro -> output key), the generator, the audit of the paper's
  source and of the rendered PDF, and their self-tests.
- `independent/`: a second implementation of the specification, written from the text alone by another AI model
  (Gemini CLI) and sharing no code, in two parts, with the comparison records; and `independent/codex/`, a third
  (Codex CLI, blind, covering the printed numbers the second did not), with its brief, ambiguities, run log, our
  value-by-value comparison and the script that reproduces each of its readings with our code
  (`CODEX_COMPARISON.md`). Its RUN_LOG.md records output hashes of an earlier, unfinished run; the comparison note
  says so and we re-ran its final code.
- **Not here, by the terms under which the database's maintainer permitted publication:** no ICIT data. No row,
  no coded text from the database, no list of texts, no list of field values, and no run output (the outputs carry
  text keys). The input file is identified by its SHA-256 only. What remains of the database here is what the rules
  need in order to be stated: the frozen specification's find-spot rule names a few area labels as examples (section
  6); the chronology rule names the area and the excavator's strata it selects (`FTrench VI`, Strata III-VII, which
  are Vats's published strata); and the specification's required tests and the records name a few rows by their row
  number only. The tests build invented rows inside themselves (e.g. the sequence `+103-104-105+` at an invented
  site), using those rule labels where a rule is tested. The original chronology test on the database's own period
  labels was withdrawn before the paper; its text is withheld (see `spec/PREREG_chronology.md`). ICIT is available
  from its maintainers (Bryan Wells and Andreas Fuls, https://www.indus.epigraphica.de/).
- **Paths in comments and records.** The code, records and frozen texts were written in a private repository and
  name files by their paths there (`submission/scripts_v2/...`, `profile/...`). `PATHS.md` (generated) maps every
  such path to its place in this repository, or says that it is a private working record and not shipped.

## Reproduce (pinned mode)

With the identical input file (SHA-256 `c02e3d7bb74cf5abb11cc94f88d8d469e6acc5d6fad4b7153c02c43428f58d98`), placed at `data/input.csv`:

    python -I -B analysis/run_core.py
    python -I -B analysis/run_full.py

Each run first checks, before it imports any analysis module, that the shipped files are exactly those in
`SHA256SUMS.txt` and each equals its entry (none missing, changed or added), then that the input's SHA-256 equals the
pin, and stops otherwise. This catches accidental and local changes; it cannot authenticate the manifest itself. The
authentic version is the tagged commit whose ID the paper prints, which fixes every byte of every file
(`.gitattributes` disables line-ending conversion, so a clone on any system arrives byte-identical). The outputs
(`analysis/out/`) are byte-identical across runs and must hash to:

- `core_fingerprints_D2a.json` `f8846c6c21cd3b351e3b1b3b034ae0ff9e86f2644606c29dbd61e5e01c9c3c76`

- `core_output_D1.json` `129ada18b41378fc26055d77cf62800c84bbd65e51d9ab4e8a3d6e6f4ef382f7`

    python -I -B numbers/make_numbers.py --check

checks those outputs against the run record's hashes and confirms that `numbers/numbers.tex`, the file every
printed number of the paper is drawn from, equals a fresh generation from them.

## Replicate (any-input mode)

    python -I -B analysis/run_core.py --any-input PATH
    python -I -B analysis/run_full.py --any-input PATH

runs the same code on another export of ICIT in the same column layout (the columns are named in the specification,
sections 0-1), writes to `analysis/out_any_input/` and labels every output as not expected to match the paper:
later versions of ICIT differ from the copy the paper measured.

## The independent implementations (with the pinned file at `data/input.csv`, from the repository root)

    python -I -B independent/gemini_v1/impl.py          # writes independent/gemini_v1/output.json
    python -I -B independent/gemini_v2/impl_v2.py       # writes independent/gemini_v2/output_v2.json
    python -I -B independent/codex/impl.py              # writes independent/codex/work/output_D0.json, output_D1.json
    python -I -B independent/codex/compare_codex.py             # after the pinned runs: value by value
    python -I -B independent/codex/reproduce_codex_readings.py  # each difference reproduced with our code

Their outputs hold whole-text keys and are not shipped either. The comparison records give the results.

## Check (tests, without any data)

    python -I -B -m unittest discover -s analysis/tests

runs the synthetic tests (fixtures built by hand inside the tests; no corpus needed). After a pinned run,
`numbers/selftest_make_numbers.py` and `numbers/selftest_audit.py` test the number pipeline with planted failures
(they read the regenerated outputs).
